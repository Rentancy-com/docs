---
title: "Webhooks"
description: "Subscribe to Lofty webhook events to receive HTTP callbacks when leads, transactions, tasks, calls, and other CRM data changes in real time."
---

Webhooks let your application receive real-time notifications when data changes in a Lofty account. Instead of polling the API for updates, you register an HTTPS endpoint, and Lofty sends an HTTP POST with a JSON payload each time a subscribed event occurs.

## Supported event types

When you subscribe, you specify a `listId` that identifies the event type you want to receive.

| listId | Event type | Triggers |
| --- | --- | --- |
| 1 | Agent Info | Agent created or updated |
| 2 | Lead Info | Lead created, updated, or deleted |
| 3 | Lead Activity | Lead site activity (browse, favorite, search) |
| 4 | Listing Alert | Listing alert changed |
| 5 | Transaction | Transaction created, updated, or deleted |
| 6 | Call | Call event (manual and logged only; excludes auto) |
| 7 | Email | Email event (manual and logged only; excludes auto) |
| 8 | Text | Text message event (manual and logged only; excludes auto) |
| 9 | Note | Note created, updated, or deleted |
| 10 | Task | Task created, updated, finished, or deleted |
| 11 | Appointment | Appointment created, updated, finished, or deleted |
| 12 | Pipeline Change | Lead pipeline stage changed |

## How to subscribe

Send a `POST` request to `/v1.0/webhook` with the event type, your callback URL, and an optional batch size limit.

```bash
POST https://api.lofty.com/v1.0/webhook
```

```json
{
  "listId": 2,
  "callbackUrl": "https://your-app.example.com/webhooks/lofty",
  "limit": 100
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `listId` | int32 | Yes | Event type to subscribe to (see table above) |
| `callbackUrl` | string | Yes | HTTPS URL that receives event payloads |
| `limit` | int32 | No | Max events per batch (default 100, max 5000) |

<Warning>
The `callbackUrl` must use HTTPS and must be reachable from the Lofty backend. HTTP endpoints are not accepted.
</Warning>

A successful subscription returns a `subscribeId` that you use to manage or delete the subscription later.

## How to list subscriptions

Retrieve all active webhook subscriptions for your team:

```bash
GET https://api.lofty.com/v1.0/webhooks
```

The response includes each subscription's `subscribeId`, `listId`, `callbackUrl`, and `limit`.

## How to delete a subscription

To stop receiving events for a subscription, delete it using the `subscribeId`:

```bash
DELETE https://api.lofty.com/v1.0/webhook/{subscribeId}
```

## Delivery timing and notification rules

Lofty typically delivers webhook events within **1 minute** of the triggering action. During high-traffic periods, delivery may be delayed but will always occur within **5 minutes**.

Notification recipients follow these rules:

1. Lofty checks which users on the lead's team have subscribed to the event type.
2. For **hidden leads**, only the assigned agent receives the notification.
3. For all other leads, the assigned agent and company owners/admins receive the notification. Other subscribers do not.

## Request format

Lofty sends a `POST` request to your `callbackUrl` with `Content-Type: application/json`. The payload contains an array of event objects. The payload structure varies by event type — refer to the [create webhook reference](/api-reference/webhooks/create-webhook) for an example payload.

A typical Lead Info event payload looks like:

```json
{
  "listId": 2,
  "events": [
    {
      "eventType": "LEAD_UPDATED",
      "leadId": 563172647619608,
      "teamId": 13233324,
      "timestamp": 1748000000000,
      "data": {
        "leadId": 563172647619608,
        "firstName": "Alex",
        "lastName": "Johnson",
        "stage": "Hot Lead"
      }
    }
  ]
}
```

<Note>
Lead IDs in webhook payloads are 64-bit integers. JavaScript clients must handle them carefully to avoid silent precision loss. See the [JavaScript and TypeScript Integration Guide](/javascript-integration).
</Note>

## Building a webhook receiver

Here is a minimal Node.js/Express server that receives Lofty webhook events:

```javascript
const express = require('express');
const app = express();

app.use(express.json());

app.post('/webhooks/lofty', (req, res) => {
  // Respond with 200 immediately to acknowledge receipt
  res.sendStatus(200);

  const { listId, events } = req.body;

  // Process events asynchronously after responding
  processEvents(listId, events).catch(console.error);
});

async function processEvents(listId, events) {
  for (const event of events) {
    console.log(`Received event type ${listId}:`, event);
    // Add your business logic here
  }
}

app.listen(3000, () => console.log('Webhook receiver listening on port 3000'));
```

## Best practices

**Respond quickly.** Your endpoint must return a `200 OK` response as fast as possible. Move any processing to a background job or async handler. If Lofty does not receive a `200` response, it may retry the delivery.

**Design for idempotency.** Lofty may deliver the same event more than once — for example, if your endpoint was temporarily unavailable during the first attempt. Use the event's unique identifier or timestamp to detect and skip duplicate deliveries.

**Validate the payload.** Check that the `listId` in the payload matches your expected event type before processing. Reject or log unexpected payloads.

**Use HTTPS.** Your endpoint must use HTTPS. Never expose a plain HTTP endpoint for production webhook traffic.

**Handle errors gracefully.** If event processing fails after you've already responded `200`, log the failure and handle it through your own retry or alerting mechanism. Lofty has already delivered the event and considers it complete once you return `200`.

<Tip>
During development, tools like [ngrok](https://ngrok.com) can tunnel Lofty webhooks to your local machine so you can test your receiver without deploying.
</Tip>

| Method | Endpoint | Description |
| --- | --- | --- |
| `POST` | `/v1.0/webhook` | Subscribe to a webhook event type |
